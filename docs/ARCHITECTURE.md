# Architecture

Source of truth: IMPLEMENTATION_PLAN.md. The bootstrap delivered daily creation/check/undo. The owner subsequently authorized a compact UI and habit management slice guided by docs/inspirations; continued work includes effective weekday schedules, detail calendars and aggregate insights.

## Boundaries

- `src/app`: Expo Router Today route and root providers. React state owns the creation form; no Zustand is needed.
- `src/components`: presentation of habit history and accessible check-in controls.
- `src/features`: repository contract and clock-injected create/toggle use cases.
- `src/domain`: validated calendar dates, history, title validation and daily streaks. No React Native, storage, network or implicit current time.
- `src/database`: Drizzle schema, synchronous repository and transactional versioned SQLite migrations; Expo SQLite provider is the native boundary.
- `src/theme`: ivory/forest design tokens and per-habit colors.
- `src/lib`: device clock/timezone adapter.

React Native/Expo supplies iOS and Android APIs. Fraunces/Inter are bundled assets. Reanimated respects system reduced motion. Database initialization failures use Expo Router's error boundary; save failures are surfaced without optimistic state loss. Repository reads/writes are synchronous and intentionally small. Revisit rendering/query strategy if measured list size makes this costly.

## Dates and consistency

Completion identity is `(habit_id, local_date)`; explicit timezone and UTC completion timestamp retain context. Calendar placement never uses the UTC timestamp. Each mutation reads one clock instant and current device timezone. Travel does not rewrite prior dates. UTC noon is used only for date-string arithmetic, avoiding DST-duration errors. Today refreshes every 30 seconds and on foreground; actions always use the fresh clock.

Daily habits begin on their creation local date. Streak counts backward from today if completed, otherwise yesterday, stopping at a missing date or starts_on. Today's pending state does not break yesterday's streak. Future and pre-creation dates do not extend it. History always preserves completed dates and distinguishes dates before creation. Selected-weekday schedules and schedule editing are deferred, so no unsupported schedule semantics are exposed.

## Storage and migrations

A named `tiny-wins.db` persists in the application's private storage. Foreign keys and WAL are enabled. Schemas v1 and v2 are applied sequentially and atomically with PRAGMA user_version; repeated startup is idempotent and unknown future versions are rejected. Add sequential migrations rather than recreating tables. Shared Drizzle schema and adapter run in Expo SQLite and in tests against better-sqlite3. Tests exercise the same migration SQL and repository, including a real file close/reopen; they do not prove the native Expo bridge or OS lifecycle. SQL schema and ORM declarations must evolve together and pass migration tests.

UUID identifiers are generated by expo-crypto. Completion writes use conflict-safe inserts, explicit deletion and foreign keys. No sync protocol, backend or speculative repositories are implemented.

## Deferred work

Detail, insights, schedule selection and export/import have been delivered in scoped tasks; dark mode remains outside the MVP. Add directories only when used. License/pricing decisions remain open. ## Browser preview

React Native Web renders the same screens for local review. The existing Expo SQLite browser worker runs with WASM and cross-origin isolation supplied by scripts/preview.mjs. No application server or mock persistence is used. This development-only adapter is alpha upstream; native lifecycle acceptance is still required. See ADR-006.

## Habit management

Schema v2 adds icons, archival timestamps and ordering. UI filters active/archived records; use cases validate edits and exclude archived habits from check-ins. Reorders are transactional and cover all active IDs. Restoration appends without changing start dates or completions. See ADR-007 and DESIGN_SYSTEM.md.

The browser worker's response-length defect is repaired by a version/source-checked postinstall script and an integration regression test. See ADR-008 before upgrading expo-sqlite.

## Schedules and progress

Schema v3 stores effective local schedule versions (ADR-009). Domain calculations remain pure; monthly/yearly calendars and insights consume the same records. Today opens detail from a name, and the historical grid opens explicit date inspection. Today, Insights and Settings are working Router tabs. The reusable focus/foreground refresh hook prevents stale views after navigation.

Type checking first regenerates route declarations through Expo's own generator, matching its CLI. This prevents an old local .expo cache from hiding/misreporting route changes; generated declarations remain untracked.

Device calendar preferences use their own repository contract, SQLite v4 singleton row and shared React context (ADR-011). Domain label/offset helpers affect presentation only; immutable local completion dates and schedule eligibility remain independent.

## Interface language

The localization feature uses expo-localization for the first preferred device language and a saved System/English/Português (Brasil) override. SQLite migration 8 adds only the constrained language preference; habit backup merge retains device preferences. The typed catalog covers app copy and accessibility; user names/notes remain literal. Presentation uses explicit Intl locales and UTC containers for immutable local dates. It does not change timezone, schedule or week-start semantics. Loading/recovery outside the database use system language. See ADR-021 and task 017 for native acceptance and platform limitations.
