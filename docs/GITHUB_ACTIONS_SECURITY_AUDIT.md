# GitHub Actions credential exposure audit — 2026-10-16

Outcome: no confirmed public Tiny Wins credential exposure found in the material examined. This is a scoped audit, not a guarantee that every possible credential format or future workflow change is safe. No real secret value was requested from GitHub, printed or written into this report.

Public repository `squiter/tiny-wins`. Initial main was `1101b2881b301929ba8ca91b0c11f4d4a2d05bdf`; concurrent release work published `059dca8`, and this audit publishes the focused artifact correction in `d0ee0f1`. Environment branch policies permit `main` and `android-v*` only for signing, `android-v*` only for publishing, and `main` only for Pages. Active rules restrict main updates and Android tag creation to repository admins; Android tag update/deletion is blocked without a bypass. No required-reviewer gate is configured; the owner deliberately selected automatic releases. Default workflow permissions are read-only and Actions cannot approve PR reviews. All seven local workflows pin actions to 40-character commit SHAs. Repository-wide policy still allows all actions and does not enforce SHA pinning; the actual audited source is pinned.

GitHub secret scanning and push protection are enabled. The available secret-scanning alerts API returned zero alerts. Non-provider patterns and validity checks are disabled; therefore zero GitHub alerts alone is not treated as proof of absence.

## Workflow and data-flow review

Initial main had six workflows. Task 034 published the seventh (`android-release.yml`) and its signing/publishing helpers during this audit. The environment-bound replacement of the legacy manual candidate is still a separate local modification. The newly added diagnostic OIDC job was separately reviewed. Source references are fingerprinted in the final audit evidence; no release tag or Play upload was dispatched by this audit.

- General verification and native development builds do not receive the four signing secrets. They run on GitHub-hosted runners with read-only permissions. There is no `pull_request_target` flow or untrusted issue/comment execution with credentials. iOS `workflow_run` acceptance requires a successful push build from main and checks artifact source identity before execution. Manual artifact selection performs the same identity checks.
- The published legacy manual candidate still references empty repository-scoped secrets and therefore fails closed. Its local replacement binds `android-signing` and this repository/main, but that file change has not been published. The automatic release workflow already uses `android-signing`. Do not copy the four secrets into repository scope to work around the legacy manual candidate; publish its reviewed environment-bound replacement separately.
- Published release automation verifies a matching tag/version and that the release commit belongs to main. Verification has no signing credentials. Signing credentials enter only the signing command step; they are not put in application config, `EXPO_PUBLIC_*`, source, a Gradle properties file or a job output. The shared app source does not read these environment variables.
- The upload keystore is decoded into `RUNNER_TEMP` with `umask 077` and file mode 0600. Cleanup removes temporary key/certificate files. Signing reads passwords from environment; keytool output is suppressed. The candidate artifact contains the signed AAB and public provenance metadata, rather than the keystore/passwords. A signing certificate inside a distributable and its fingerprint are public by design.
- Publishing has a separate environment/job, no upload-key secrets and only publication and the explicitly restricted diagnostic auth-check job request `id-token: write`. The pinned Google auth action requests a 600-second Android Publisher access token, disables credential-file creation and environment export, and passes the token only to the API client step. The client rejects redirects and prints controlled errors, rather than response bodies, request headers or nested network diagnostics. The source Google trust condition binds repository ID, owner ID, Android tag, workflow path and `android-publish` subject. GitHub OIDC uses an immutable subject with repository/owner numeric IDs, and the helper was updated to match it. Live Google IAM/trust policy was not independently audited here. The diagnostic run 38981458656 initially failed, then succeeded on attempt 2 after the parallel setup correction. Both attempts were scanned; the successful run visibly masks the token environment value, prints only a controlled success summary and has zero Gitleaks indicators. It performs no signing, Play API call or artifact upload.
- Upload paths were followed for debug APKs, unsigned iOS simulator archives, Pages, audit JSON, synthetic acceptance screenshots and logs. The iOS smoke folder contains synthetic test evidence; that job has no signing or Google credentials. Dependency caches cover npm packages, not release key files. No environment dump, shell tracing or direct secret echo was found in the audited workflow/helper paths.

## Examination and tests

Final counts and machine-readable outcomes are in [the audit evidence](../.harness/evidence/035-security/summary.json).

- 246 original retained runs, plus two completed runs published during the audit; 249 log archives total including both OIDC attempts. Gitleaks/decoded-content inspection of these logs reports zero indicators.
- All 169 original available artifact manifests inspected (2,311 outer ZIP entries), zero recognized credential filenames. Text/config/log members were read completely for 168 artifacts; artifact 12064947466 (`tiny-wins-ios-smoke`) remains partial after a connection reset on the second attempt. Already retrieved text from that artifact was included in the scan. No third identical retry was attempted without a new remedy.
- 1,470 extracted text/config/log files, approximately 14.67 GB, split into immutable snapshots for the final scanner. Media and most nested historical native binaries received filename/structure review rather than exhaustive OCR/decompilation. Six selected complete artifacts had additional recursive byte-pattern inspection, including two Android APKs.
- Initial explicit-pattern pass covered 972 historical Git blobs (26.7 MB); the later specialized history scan covered all available refs and reported one manually verified file-digest candidate. A separate current-source snapshot also reported only that digest. No private credential file was added to the repository.

The first pass used explicit credential patterns on retained logs, historical Git blobs and selected complete artifacts. An independent official Gitleaks v8.30.1 binary was downloaded to a private temporary directory and its release checksum verified. Default rules plus decoding/archive support were used for source/history/logs and extracted artifact text. Reports were redacted and kept outside the repository. No scanner allowlist or finding suppression was introduced.

Gitleaks reported one source/history candidate: `.harness/evidence/028-android/acceptance-summary.json:90`, the SHA-256 recorded for `src/theme/tokens.ts`. Recomputing that file's SHA-256 exactly matches the recorded value; this is a file-integrity digest, not a credential. The same candidate in history/current source is one underlying false positive. Artifact scanner candidates were retained for review and originated in raw `device-simulator.log` system dumps: TCC request IDs, WidgetKit locale IDs, UUIDs, telemetry correlation values, system hash/key-like identifiers and Apple MobileAsset decryption metadata. Raw scanner exit 1 is reported honestly; these results are classified rather than suppressed or presented as a mechanical zero-finding pass.

`npx vitest run tests/integration/android-release.test.mjs tests/integration/android-release-automation.test.mjs` passed 24 tests. After adding the artifact regression and incorporating the concurrent OIDC checks, `npm run verify` passed 118 unit + 57 integration tests (175 total), strict types/lint/format and all platform exports. Two additional CLI checks used synthetic canaries in an HTTP response body and a network exception/header/cause object. Both failure paths exited closed without including the canary in stdout/stderr. These checks never contacted Google or used real keys.

## Limits and next steps

GitHub will not return stored secret plaintext, so exact matching against the four real secret values is impossible through its API. Pattern/decoded-content scans and data-flow review reduce risk but do not prove absence of every arbitrary password or encoded payload. Archived videos/images and most historical compiled binaries were inventoried by ZIP member names rather than exhaustively decoded/OCR'd; selected complete artifacts received an additional byte/recursive-archive scan. Deleted runs, removed artifacts, attacker-held copies and future executions are outside this snapshot. The real OIDC diagnostic has been examined, including success and failure. Hosted signing and actual Play publication have not been exercised in the examined history; their future logs cannot be certified by this audit.

No evidence of Tiny Wins credential exposure justifies rotating/deleting working signing secrets, deleting public logs/artifacts or changing permissions automatically. Keep secrets environment-scoped, retain short-lived OIDC credentials and inspect the first hosted signed build/publication logs and artifact allowlist before enabling distribution. Consider enforcing commit-SHA pinning at repository policy level as additional protection; it is a separate permissions change. The audit changes only the iOS evidence upload allowlist and a regression check, plus this report/evidence. No permission, secret value or concurrent task 033/034/owner roadmap edit was changed.

## Preventive correction

The historical `tiny-wins-ios-smoke` upload included an entire simulator output folder. Its raw `device-simulator.log` files contain Apple OS request/locale/correlation identifiers and MobileAsset archive-decryption metadata unrelated to Tiny Wins signing/Google access. Some are flagged by generic credential rules; Square-token candidates in the first pass were verified to be parts of ordinary OS UUIDs. These are retained as classified findings, not silently suppressed or represented as leaked Tiny Wins credentials. The final evidence includes exact category counts without copying any candidate values.

The final broad folder upload is replaced with explicit test report, synthetic screenshot, hierarchy and Maestro/XCTest log paths. Hierarchy uploads accept XML/JSON, screenshot uploads PNG; raw OS logs, arbitrary files and credential filenames are excluded. The two earlier failure/compact upload steps receive the same typed hierarchy/screenshot restrictions where needed. A regression exercises real glob matching to verify that required evidence remains included while simulator logs and sample credential paths are rejected. Previously published historical artifacts are not silently deleted by an audit; no Tiny Wins key/token leakage was established. Public artifact hygiene is improved for subsequent runs without weakening acceptance assertions.

The final artifact scan reports **3,296 raw candidates** (3,272 generic and 24 Square-pattern matches), all confined to raw simulator OS logs and classified in the evidence. No unclassified candidate remains in the scanned text. The 24 Square-pattern matches are verified substrings of OS UUIDs; the generic candidates include 129 MobileAsset archive-decryption metadata entries. These platform values are not reproduced. They justify the upload minimization; they are not described as Tiny Wins signing/API secret leaks.
